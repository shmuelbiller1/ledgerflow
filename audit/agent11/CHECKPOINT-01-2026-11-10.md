## Findings so far in my lane (imports / exports / documents)

### J-1 — export → import round trip changed the data. **FIXED, tested, pushed.**

Mechanism: `sanitizeCsvCell` (src/lib/csv.ts) writes a leading apostrophe in front of any text a
spreadsheet would run as a formula (`=`, `+`, `-`, `@`, tab, CR). Every CSV export goes through it. The
record import (Settings → Import data) had no matching step, so re-importing an exported customer list
changed the values:

| Value as stored | Cell in the exported CSV | Value after import (before the fix) |
|---|---|---|
| `+1 555 0100` | `'+1 555 0100` | `'+1 555 0100` |
| `-call before 10am` (note) | `'-call before 10am` | `'-call before 10am` |
| `-Discount Customer` (name) | `'-Discount Customer` | `'-Discount Customer` |
| `+972 3 555 0101` | `'+972 3 555 0101` | `'+972 3 555 0101` |

Reproduction: `audit/agent11/probes/j1-export-roundtrip.ts` and `j1b-roundtrip-cleanup.ts` (executed).
The import's own clean-up (`cleanupContactImportRows`) does not remove it, so the screen path also changed it.

Fix: `unguardCsvCell` in `src/lib/csv.ts` removes exactly the guard this app wrote and nothing else
(a real name beginning with an apostrophe, `'Round Table Ltd`, is untouched; a plain number `-1,000.00`,
which was never guarded, is untouched). Applied once, at the top of `readValue` in
`src/lib/recordImport.ts`, so every import field and both the preview and the server-side check see the
same corrected text. Tests: `src/tests/j1-export-import-roundtrip.test.ts` (4).

### J-2 — the QuickBooks Online migration wizard did not use the shared CSV reader. **FIXED, tested, pushed.**

`src/components/migration/QBOMigrationWizard.tsx` hand-rolled a CSV parser (a split on line breaks, then a
character loop). Executed side by side with `src/lib/csv.ts` (`audit/agent11/probes/j2-qbo-wizard-csv.ts`):

| Input | Wizard (before) | Shared reader |
|---|---|---|
| memo with a line break in quotes | **split into two rows** (`first line` / `second line`) | one cell `first line\nsecond line` |
| `"He said ""paid"" today"` | `He said paid today` (quotes **deleted**) | `He said "paid" today` |
| European `;` export | one column `2026-01-05;Acme;paid` | three columns |
| truncated file (unclosed quote) | accepted silently | `parseCsvChecked` refuses with a message |

Effect on a real migration: a QuickBooks memo/description that contains a line break shifts every later
column of that row, and a dropped quote silently alters imported text. Fix: the wizard now calls
`parseCsvChecked` from `src/lib/csv.ts`. Tests: `src/tests/j2-qbo-migration-shared-csv.test.ts` (5).

### J-4 — `.xlsx` support is partial, and one screen claims `.xls` it cannot read. **OPEN (finding, no fix yet).**

- Settings → Import data (`accept=".csv,.txt,.xlsx,.iif,.qbi,.vcf,…"`) does read `.xlsx` through
  `parseExcelToRows` → `exceljs` (lazy `await import('exceljs')`, already in the bundle and excluded from
  the PWA precache by `pwa-bundle-optimization.test.ts`). Good.
- **`QBOMigrationWizard` accepts `.xls`** (`accept: { 'application/vnd.ms-excel': ['.xls', '.xlsx'] }`,
  and its on-screen help says "Supports .csv, .xlsx, and .xls exports") but the parser is `exceljs`, which
  **cannot read legacy BIFF `.xls`**. A user who drops a real `.xls` gets a raw parse error. Either the
  claim goes or a converter is added — owner/lead decision.
- Every other importer (bank statements, payroll provider CSV, price list, corporate card, GSA per diem,
  migration trial balance proof, Xero documents) is CSV-only by design and says so in its own words; that
  matches the queue text ("the importers" = the list importers), so no defect claimed.

### J-6 — the invoice/statement PDF does **not** print the tax number or the customer's address. **OPEN (finding).**

Executed the real generator (`generateDocumentPdf`, `src/server/services/pdfService.ts`) and read the PDF
text back (`audit/agent11/probes/j6-invoice-pdf-content.ts`):

- Workspace name ✔, workspace address ✔ (three lines), logo ✔ (`logoBytes(branding.logoDataUrl)`),
  document number ✔, dates ✔, customer **name** ✔, Hebrew/bidi words ✔ (`מספר`, `תאריך`, `לתשלום עד`).
- **Workspace tax number `515123456`: absent.** `layoutDocumentPdf` builds `company: { name, addressLines }`
  only — there is no tax/VAT number field anywhere in the layout or the header.
- **Customer address `1 Main St / Spring Valley NY 10977` and customer tax ID `12-3456789`: absent.**
  The recipient block prints `doc.customerName` only (`recipient` at pdfService.ts:196-197); no address
  lines, no customer tax id.
- Long descriptions **do** wrap (`wrapText`, pdfText.ts) rather than being cut — queue item satisfied.
- Side observation: with the fallback Helvetica font (embedded DejaVu missing) the probe showed mojibake
  for `ILS 1,234.56`, `Short line` and some digits. The DejaVu fonts are committed
  (`src/server/assets/fonts/`), so this is the documented no-font fallback, not a live defect — recorded
  so nobody re-reports it as one.

Severity: an Israeli tax invoice legally needs the supplier's ע.מ/ח.פ and, for a Tax Invoice to a
business, the customer's name **and address**; a US invoice needs the seller's EIN on request. This is a
**P1 for real bookkeeping**, not a Stage-A blocker. Not fixed here: PDF layout is AI #1's lane
(`src/server/`), and the queue's J-6 explicitly says "report", not "patch the server".
