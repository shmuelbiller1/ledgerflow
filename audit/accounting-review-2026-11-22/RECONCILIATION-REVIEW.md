# Bank reconciliation review — partial (in progress)

## BR-01 — P1: searching hides selected entries from the balance calculation but still clears them

**Independent example:** No beginning balance; one $100 deposit in the bank account; statement ending balance $0. Select the deposit in the reconciliation wizard. It should not be possible to complete a $0 statement with that $100 deposit as a cleared item: the reconciliation has a $100 difference. Type a search term that hides the selected deposit. The component calculates the difference from the *filtered visible* transactions only, now treating the cleared total as $0, but still sends the deposit's ID in `reconciledIds`. It permits finishing with a $0 difference and sends $0 plus the selected $100 deposit.

**Evidence:** `reconciliation-search-ui.test.tsx` reproduces the interaction against the real React component using simulated DOM and synthetic store state. `reconciliation-complete-database.test.ts` separately sends that class of request to the real transaction router with injected owner identity and isolated PostgreSQL; the server writes a `completed` reconciliation and marks the receipt `reconciled` and `isCleared`. These are complementary tests, not a single authenticated-browser-to-DB test. No real statement, customer or hosted environment was used. Selecting a transaction and then searching is an ordinary interface interaction; date/account changes can also hide selections in code, but those variants are untested. The UI does require zero difference, but it calculates the difference incorrectly after filtering.

**Mechanism:** `ReconciliationWizard.tsx:90–117` filters by search before calculating selected totals; `:152–165` checks that result then submits the unfiltered selected ID list. `reconciliationWriteService.ts:672–730` records completion without independently recomputing the accounting agreement. This can make an unreconciled deposit disappear from future outstanding lists and establish an incorrect starting balance for a subsequent reconciliation. It does not alter the posted journal's money lines in this test.

**Acceptance:** Calculate selected totals from all eligible selected transactions independently of presentation search; remove or revalidate selections on account/date changes; have the server atomically verify the account, dates, starting balance, full selected cash-leg amounts and statement difference rather than trusting UI calculations. Cover search, filters, changing dates/accounts, duplicate IDs, retries, concurrency and locked periods. Distinguish documented legitimate reconciling items from merely accepting a mismatch.

## BR-02 — P1: completion endpoint accepts future and unrelated entries and any supplied statement balance

The same local-DB test additionally submits a June 1 expense/A/P journal with **no bank leg** as a reconciled entry for a **May 31 bank statement**. The real completion endpoint accepts it, persists a completed reconciliation, and sets the unrelated June journal to `reconciled` and `isCleared`. The request also reports a zero ending statement balance while selecting the $100 bank receipt. The server validates workspace membership, roles, account existence, statement-date lock and draft/void status, but it does not validate the selected account's cash legs, dates, balance arithmetic or prior reconciliations (`reconciliationWriteService.ts:650–730`). The latter statement specifically describes this completion path; other bank-line matching paths have their own direction/account validations. The extra unrelated future ID was a **crafted request**, not shown reachable from the usual UI. The command description says not to use it before the statement agrees, but it is callable through the registered route, so caller intent is not a server-side safeguard.

## BR-03 — P1: first reconciliation mistakes current balance for beginning balance

**Worked case:** A checking account has a genuine $0 beginning balance and one posted $100 receipt, which appears on the bank statement. Its current computed book balance and statement ending balance are both $100. In a first reconciliation with no previous statement, the wizard uses the **current $100** as the beginning balance because `openingBalanceCents || balanceCents || 0` treats a legitimate zero as absent. It reports zero difference and allows completing the $100 statement with **no transactions selected**, leaving the $100 receipt uncleared. If the receipt is selected, its amount is added again to the already-current balance. A first reconciliation must base the calculation on the prior statement/opening point, not a balance already containing the entries to be selected.

**Evidence/scope:** A second test in `reconciliation-search-ui.test.tsx` reproduces completion with a computed-account fixture in the real component and simulated DOM. `Ledger.tsx:82–89, 696–701` passes computed or server-derived account balances to the wizard; `useLedgerStore.ts:335–379` explicitly computes `balanceCents` from opening plus transactions. This is not an authenticated end-to-end browser/DB reproduction, and initial balance provenance and reconciliation conventions vary by migration. No conclusion is made about accounts with an existing reconciliation or a nonzero recorded opening balance.

**Acceptance:** Preserve explicit zero, obtain the actual prior statement/opening balance as of its effective cutoff, and avoid counting the same journal in both beginning and selected movement. Use an authoritative server-validated reconciliation and test first-ever reconciliations, imported openings, zero and nonzero beginnings, backdated activity and incomplete history.

## BR-04 — P1: automatic matching can clear an $100 statement line against a $20 bank movement

**Worked case:** A $100 bank deposit line and a same-day, similarly described balanced entry: debit cash $20, debit A/R $80, credit sales $100. The entry header total is $100, but the only movement in this bank is **$20**. A single automatic one-to-one match cannot explain the other **$80**; it needs other cash entries or an explicit correction/reconciling item. The actual **Auto-match all** component action sends a request to mark that line matched and the entry reconciled, because its scoring treats either the cash leg *or the journal header total* as an amount match (`reconcileActions.ts:189–213`). It applies the selected pairs directly. The separate local-DB route test sends that same operation pair and confirms the line becomes `matched` and entry becomes `reconciled`: the server verifies cash account and direction, but not the amount (`reconciliationWriteService.ts:20–55, 289–306`). The screen's manual comparison does display amount differences; this finding concerns the distinct automatic action.

**Evidence/scope:** `reconcile-auto-mismatch-ui.test.tsx` exercises the real component and action in simulated DOM with fake network responses; `reconcile-auto-mismatch-database.test.ts` separately uses the real route, seeded balanced journal and statement line, injected owner, and isolated DB. It is not a single real-browser/provider test, nor proof of actual customer impact. Neither test changes the ledger's cash amount; the problem is a falsely matched/cleared status. Matching fees, grouped deposits, partial settlements, FX, and supported tolerance policies require explicit documented reconciliation amounts rather than assuming the journal header is the bank movement.

**Acceptance:** Automatic one-to-one matching must use the correct account's signed cash leg and an explicit supported tolerance or explainable allocation, with no silent full match on the journal total. Verify and persist amount/remaining differences at the server; test split journals, transfers, grouped deposits, fees and concurrent matching.

## BR-05 — P1: two separate bank lines can both be marked matched to one $100 journal

The real batch route accepts a crafted request to match **two distinct $100 deposit lines** to the **same $100 bank entry**, with one transaction-status update. Both statement lines become `matched` and the single entry becomes `reconciled`, apparently clearing $200 of bank activity against $100 of ledger activity. In the synthetic case, both statement lines are independent and each has the full amount; a legitimate many-to-one match would require explicit aggregation and amounts that reconcile, neither of which is represented here. Each line has the right account and direction, so that existing guard does not catch the double use. `reconciliationWriteService.ts:130–151, 289–306` checks repeated updates to the *same line* and repeated transaction operations, but does not ensure distinct matched targets or track allocated amounts.

`reconcile-duplicate-database.test.ts` reproduces the crafted request against the real router with injected owner and local PostgreSQL; normal UI generation, concurrent requests, reversals and actual customer impact remain untested. The UI's global match algorithm seeks one-to-one pairs, but server-side invariants must hold for every authorized caller and race. Enforce an atomic, tenant/account-scoped allocation invariant with uniqueness or explicit split totals and correct unmatch behavior; test multiple lines in one batch, retries, separate simultaneous requests and already-matched entries.
