## 1. A-259 — keyboard path on five busy screens

**Two real defects were in the way, both fixed and pinned by tests.**

**(a) Six dialogs announced `role="dialog"` but had no keyboard behaviour at all** — focus never
moved in, Escape did nothing, focus never returned. They are the row dialogs of exactly these
screens: Make deposit (Banking), Spread (Sales/Purchases rows), Apply/refund credit (credit
notes), bank-line Pay/Split (Reconciliation), Email invoice (Sales row), and the inline Add a
fixed asset dialog. All six now use the shared `useDialog`, mechanically (`{...dialogProps}`,
`id={titleId}`), nothing else in them changed. `src/tests/dialog-keyboard-a259.test.tsx` pins
focus-in → Escape → focus-back for each (**7/7**, including the guard below).

**(b) Hover-only row actions were invisible to a keyboard user.** Containers with
`opacity-0 … group-hover:opacity-100` hide their subtree — including the focus ring of a button
that holds keyboard focus. Sales invoice/customer rows, TaxManager, Inventory, BudgetManager,
Vault delete, SplitEditor remove, the attachment-remove button and the Saved Views pin now also
reveal on `group-focus-within` (the pattern Reconciliation and TransactionRow already used).
A source guard in the same test file holds it, with the 8 remaining decorative cases named in an
allowlist (card sheen, chart tooltip, drag grip, drill icons, palette hint).

**The Chromium proof** — `e2e/keyboard-busy-screens.spec.ts`, one test per screen on the shared
journey harness at desktop width: focus the row button (ring shown, effective opacity 1), Enter
opens its dialog, focus lands inside and Tab stays inside, Escape closes, **focus returns to the
row button**. Sales: Edit invoice 1001. Purchases: Edit bill 2001. Banking: Make deposit (plus
the account card's Sync Feed focus). Reconciliation: select the bank line, then Split.
Settings → Users: the member row's Revoke → Remove dialog.

**Plus #104's browser re-check** — `e2e/ledger-grid-keyboard.spec.ts`: on the real Transactions
screen the grid region takes focus, arrows move the announced highlight ("Row 1 of 2" → 2 → 1 →
End), the announced row is drawn in the viewport, Tab/Shift+Tab leave the region, Escape clears
the announcement. The 200-row scroll mechanics stay with the unit suites (they assert the
`scrollToItem` call); the demo books have two entries, and the spec says so.

## 2. #146 — Escape after focus drifts (mechanism fix, shared hook)

A modal only heard Escape when focus was inside it. When the focused control unmounts or disables
(a Save button after its save lands — the record-details drawer's flow), the browser drops focus
to the body and Escape went dead behind a modal; that is the load-dependent flake filed as #146.
`useDialog` now also listens at the document in the capture phase and answers Escape only when the
dialog is the topmost open one (deepest in the DOM, then latest opened — child effects run before
parent effects, so registration order alone names the wrong one) **and** the event did not start
inside it, leaving field-level Escape handling (InlineEdit cancel) exactly as it was. Two new
tests pin the drifted single and nested cases. **Honest limit:** the original failure is load-only
and was not reproduced in this session; this closes the mechanism it points at, and the next
full-suite runs are the evidence either way.
