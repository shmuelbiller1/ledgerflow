## 1. A-257 — CodeRabbit follow-ups on PR #436

**(1) A retry left the screen neither failed nor loading.** `retry`, `retryTransientFailures` and
`retryAfterReconnect` in `src/stores/useDataNeedsStore.ts` used to clear `failed[key]` while the
old `loaded[key] = true` stayed, so the notice vanished and the screen went straight back to its
possibly-stale list while the reload was still in flight. Fix: every retry path now sets
`loaded[key] = false` for the cleared keys, so `useLedgerCollections` / `useScreenDataHealth` /
`DataStatusBar` all read *loading* until the fresh snapshot's `markLoaded` arrives. A `retry` on a
key with no failure and no retry plan is now a no-op, so a healthy live collection is never sent
back to "loading" (its subscription never stopped — there would be nothing to arrive).

- Store-level proof: `src/tests/collection-retry.test.ts` — two new tests: all three retry paths mark
  the collection loading and then ready on `markLoaded`; a refusal is never reclassified as loading
  by the reconnect path; `retry` on a never-failed loaded key returns the same state object.
- Screen-level proof: `src/tests/screen-data-states.test.tsx` — new "A-257" test on Sales: fail
  invoices, press **Try again** → notice gone, `Loading invoices…` shown instead of the empty list;
  `markLoaded('invoices')` → spinner gone, the true empty state back.

**(2) Health keys already at target on `main`.** Verified in this checkout: TaxManager
`['transactions', 'taxRates', 'accounts']`, Purchases `['bills', 'vendors', 'recurring', 'accounts']`,
Sales `['creditNotes', 'customers', 'invoices', 'payments', 'accounts']` — `accounts` is in all three;
Reconciliation `['transactions', 'accounts', 'bankLines']` with the source comment "matching reads
entries, accounts and the bank feed (not saved reconciliations)". Nothing left to change.

**(3) The 44 px row buttons measured in Chromium.** `e2e/phone-tap-targets.spec.ts` (via the shared
`e2e/support/journeyFixture.ts` harness — stores seeded, database/API boundary stubbed, exactly the
seeding CodeRabbit's note suggested): at 390 × 844, on Sales → Customers & Clients the
`button[title="Enter Invoice"]`, **Archive Acme Corp** and **Delete Acme Corp**, and on Purchases →

## A-260 note (dark-theme contrast, same branch)

The axe half of A-260 is **already at target on `main` and stays there on this branch**:
`e2e/contrast-baseline.json` holds **0 failing elements for every key** (`light:`/`dark:` × the six
main views, plus dark Banking / Reconcile / Balance sheet / Trial balance / Taxes), and CI green
means every screen meets it. The remaining piece — an app-wide unit check of the
background/foreground pairs so a palette edit fails before a Chromium shard does — is
`src/tests/theme-contrast-pairs.test.ts` (**51/51 pass**): it parses both theme blocks out of
`src/index.css`, computes WCAG ratios per pair, and holds each at-or-above-AA pair to the 4.5 bar
while the two measured dark offenders — `--faint` on `--elevated` (**4.13:1**) and `--neg` on
`--elevated` (**3.89:1**) — get per-pair floors that may only go up. Raising those two is a palette
change, and a palette change regenerates every `e2e/__screenshots__` reference image — that needs
a machine with a browser, so it is **deliberately deferred** to a Chromium session (they do not
surface in axe today: nothing renders those two pairs as text-on-that-background on the covered
screens).
