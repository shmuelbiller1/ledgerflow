## A-269 — the passkey ceremony in a real browser

`e2e/passkey-signin.spec.ts`, **2/2 Chromium**, run three times in a row (5.4 s, 4.9 s, 5.3 s) and
once more after the final cleanup edit.

**Why it is stubbed at the server and real in the browser.** There is no reachable Supabase project
in this sandbox, so `stubAuthServer()` intercepts only
`https://ledgerflow-unconfigured.invalid/auth/v1/passkeys**` and answers the six calls
(`registration/options`, `registration/verify`, `GET`, `PATCH`, `DELETE`, preflight). Everything the
test is actually about stays real: the page's own `registerPasskey()`, `navigator.credentials.create()`,
the platform authenticator, the CBOR attestation, the relying-party check, and the screen that lists
the result.

**The authenticator** is Chromium's own, added over CDP:

```ts
await cdp.send('WebAuthn.addVirtualAuthenticator', {
  options: { protocol: 'ctap2', transport: 'internal', hasResidentKey: true,
             hasUserVerification: true, isUserVerified: true, automaticPresenceSimulation: true },
});
```

Measured after the click:

- the authenticator holds **1 credential**, `isResidentCredential: true`, and its `rpId` is the page's
  own host `localhost` — the browser bound the credential to this origin, not something the test told it;
- the `registration/verify` POST carried that credential's id (the stub only writes a row when
  `challenge_id` matches and `credential.id` is non-empty, and returns 400 otherwise; it does not compare that
  id with the authenticator's own credential);
- Settings → Security listed `Remove Work laptop` and `1 passkey can sign in to this account.`;
- reopening the screen (Settings → Security again) still showed `Remove Work laptop`, read back from
  `GET /passkeys`.

**The refusal case.** With the server answering `422 {code: 'passkey_disabled', msg: 'Passkeys are not
enabled for this project'}` at `registration/options`, the screen shows an `alert`, the authenticator
still holds **0** credentials, and no `Remove …` row exists. The panel reports the server's own reason
verbatim rather than inventing a success.

**Two test-side notes worth keeping** (both were real red runs first):

1. The panel has **two** `role="status"` regions after a successful add (`No passkeys yet.` / `Passkey
   added…` / the count sentence live in different polite statuses). An unscoped `getByRole('status')`
   is a strict-mode violation — the spec scopes by text.
2. The verify POST can land a tick **after** the credential exists on the authenticator, so the row
   count is polled, not asserted once.

`navigator.credentials.create()` also refuses to run in a page without a session, so the test writes a
Supabase session to `localStorage['sb-ledgerflow-unconfigured-auth-token']` (the key is
`sb-<first host label of the auth URL>-auth-token`) before loading the page. Cleanup always calls
`WebAuthn.removeVirtualAuthenticator` and `WebAuthn.disable`.

**A copy nit for the lead, not filed as a bug:** `src/lib/db/auth.ts` has the sentence "Passkeys are
not turned on for this site yet." for the disabled case, but the panel surfaces the server's raw
message instead, so a user can read Supabase's internal project wording. `passkeysOff()` already
recognises the error; choosing to show the plain sentence belongs to whoever owns the auth copy.

## A-270 — the Reports keyboard path

`e2e/keyboard-reports.spec.ts`, **2/2**, plus `src/tests/aging-views.test.tsx` **5/5**.

The app changes are small and in `src/components/reporting/`:

- `PartyAgingReportView.tsx` — each customer/vendor row is now a keyboard target:
  `tabIndex={0}`, `role`/button semantics with `aria-label="Open the customer aging detail for …"`,
  Enter **and** Space both open it. The key handler only fires when
  `e.target === e.currentTarget`, so the arrow button inside the row keeps its own Enter;
- closing the drawer returns focus to the exact row that opened it (`openerRef` + `requestAnimationFrame`
  after unmount — focus cannot be restored to a node that is still being removed);

  `aria-pressed={timeframe === t}`, so the screen states which period is showing.

What the browser proves:

- `Tab` from `Search by customer` lands on the first row (there is a row with a real balance);
- `Enter` on that row opens the drawer named `Outstanding Ledger: <customer>` and focus is **inside** it;
- `Escape` closes it and focus is back on the **same** row — compared by `aria-label`, not by index;
- the row's arrow button also round-trips, including the drawer's own Back button;
- `Month`, `Quarter`, `Year` report `aria-pressed` truthfully, and `Select Month` moves the period
  independently — the shortcut state follows;
- `Choose report` → `journal-sheet` opens the Journal Sheet (the picker stays reachable by keyboard).

*Note:* `page.pdf({ format: 'Letter' })` does **not** override the app's own `@page`; the select is the

## Issue #146 — the nested drawer's Escape, proven in a browser (`946688c`)

Issue #146 was filed from a load-only flake: a nested **Edit record details** drawer stayed open on
Escape. The cause is focus, not the drawer's listener. `Save details` disables itself for the write
(`Saving…`), the browser then drops focus to `document.body`, and an Escape that starts outside the
dialog never reaches the dialog's own keydown handler. `useDialog` already answers that at the
document in the capture phase, for the topmost dialog only, but nothing had ever proved it in a real
browser against the real drawer — the existing unit test *simulates* the blur.

`e2e/issue-146-drawer-escape.spec.ts` (**2/2**, three consecutive runs; neighbours `record-details`,
`customer-tax-certificates`, `vendor-tax-records` also 5/5 together) mounts the real
`RecordDetailsPanel` over the real `BillModal` and makes the write slow on purpose (1.2 s), so the
disabled-button window is observable:

- `Save details` → `Saving…` disabled, and **focus is on `body`** — the issue's precondition, measured;
- `Escape` closes the drawer **alone**: the bill stays, its vendor draft is intact, and nothing was saved twice;
- the accepted write **still lands after the drawer closed** (counted in the page), and a reopened
  drawer reads the new address back;
- one Escape closes one dialog: the reopened drawer first, then the bill (whose draft asks before closing).

**The test is not vacuous.** With the document-capture handler removed from `useDialog`, the same
sequence gives `focus=body`, `drawerOpenAfterEscape=1` — the issue's exact symptom. The hook was then
restored unchanged (`git diff` empty), so this commit adds evidence only: **no production code
changed** for #146, because the fix was already in `useDialog` and `useDialog`'s unit tests.

## Issue #274 §1 — the Settings reveal, measured (`632cc41`)

`#274`'s first half: choosing a section from the Settings shortcut grid changed the selection while the
panel stayed below the fold, so the buttons looked dead. The fix (scroll the panel into view, move focus
to it) has a jsdom test, but that can only assert `scrollIntoView` was **called**.

`e2e/settings-section-reveal.spec.ts` (**2/2**, phone 390×760 and desktop 1280×800) measures the reader's
view instead: **before** the click the open panel sits entirely below the fold (top > viewport height —
the reported bug), and after choosing Developer its top is inside the viewport and the panel itself holds

the test non-vacuous — no production flag was needed. No production code changed.
